# gd-crm-sanfang-daily

内网 GD-CRM「三方营销」媒介日报的**执行说明书**：一键脚本取数 → 区间报表唯一真值 → 三方聚合 → 单文件 HTML 趋势报告，附口径核对与「假成功」识别。

> ✅ **clone 即可部署**：`runtime/` 里带 14 个可移植脚本 + 图表库，新电脑装完依赖、填好凭据就能出报告。**完整部署步骤见 [`runtime/DEPLOY.md`](gd-crm-sanfang-daily/runtime/DEPLOY.md)**。
> ⚠️ 两个硬前提：**新电脑必须能连公司内网 `192.168.16.138`**（缺 VPN 就出不了数，别去改代码）；**账号密码不在仓库里**，要自己把 `config.example.json` 复制成 `config.local.json` 填写。
> 生产真源仍是项目工作区 `gd-crm-媒介日报\`，`runtime/` 是发布副本，方向单向；源目录改了逻辑跑 `tools/sync_runtime.py` 重新同步，别手工两边改。
> 另：说明书与脚本含公司内网地址、接口结构、真实历史业绩数字与内部账号 ID，公开即对外可见。

## 一、它到底做什么

一句话：**每天把内网 CRM 里「媒介类型 = 三方营销」的明细行捞出来，算成一份能和 CRM 当面对账的 HTML 趋势报告，并且能在脚本崩了的时候拦住一份「看起来成功」的假报告。**

它不是通用报表工具，而是把这套特定系统的取数窗口、口径陷阱、验收标准和汇报格式全部固化下来，让每天 08:00 的定时任务**无需人盯**也能跑完闭环。

| 环节 | 内容 |
|---|---|
| **数据源** | 内网 GD-CRM 的「网电咨询师媒介 / 渠道报表」，只取 `媒介类型 = 三方营销` 的明细行 |
| **统计窗口** | 当月 1 号 ~ 前一天，由程序二分探测 CRM 当前可查首日自动决定，**不手工指定** |
| **核心中间数据** | `window.json`（窗口）、`range.xls` + `range_baseline.json`（区间报表真值）、`sanfang.json`（聚合结果，下游共用） |
| **主交付物** | `三方营销媒介分析报告.html`（单文件，主文件同名覆盖，生成时自动留档到 `history\`，同窗口同 md5 去重） |
| **汇报内容** | 报告路径 → 实际统计区间（天数 + `queryable_start`）→ 区间合计四项 → 最新一天四项 + 环比 → 异常清单 → 一句话结论；另附口径差与校验结果 |
| **下游** | `weekly-report-fill` 消费 `sanfang.json` 的 `window_totals / total_trend / daily_sum / src_total / emp_total / dates / window` 填周报，**共用取数层** |

四项核心数 = 建档量（报告里显示「录单」）、来院总人数、成交总人数、成交总金额。转化率与客单价都由这四项现算。

## 二、六步流水线（`run_daily.py` 内部顺序）

| # | 脚本 | 干什么 | 产物 |
|---|---|---|---|
| 1 | `fetch_window.py` | 二分探测 CRM 当前可查首日，按整月区间导出区间报表 | `window.json`、`range.xls` |
| 2 | `batch_fetch.py` | 只补抓区间内缺失的**单日** xls（**仅供画逐日曲线，不参与合计**） | `data/raw/daily/*.xls` |
| 3 | `parse_daily.py` | 单日 xls → json | `data/analysis/daily/*.json` |
| 4 | `build_range_baseline.py` | 区间报表 → 合计 / 媒介 / 咨询师 / 五档的**唯一真值** | `range_baseline.json` |
| 5 | `analyze_sanfang.py` | 合并成最终结果，打印累计行 | `sanfang.json` |
| 6 | `gen_report_sanfang.py` | 生成 HTML + 自动留档快照 | 主报告 + `history\` |

**parse / baseline / analyze / gen 四步全绿才留档**，否则 `archive_report()` 会跳过，避免把假成功版本存进历史。整个流程约 1~8 分钟（含逐日补抓），属正常，别中途当卡死杀掉。

## 三、核心能力清单

1. **自动探测可查窗口** —— 不问用户要日期，自己二分找出 CRM 现在查得到的第一天；查不到的日期一律不纳入、不补齐、不推算。
2. **区间报表唯一真值** —— 合计一律取 CRM 区间报表逐格结果，**绝不叠加本地存档、绝不用逐日相加当合计**（曾有人用存档补月初算出 308 人来院，被当场否掉）。
3. **假成功识别** —— `analyze_sanfang.py` 必须打印「建档 X | 来院 X | 成交 X 人 | 业绩 X 元」累计行；**没有这行 = 分析崩了**，而 `gen_report` 仍可能拿旧 json 出一份「看起来成功」的 HTML。此时判失败、不许沿用上一版报告。
4. **口径对账** —— 逐日相加 vs 区间报表差 3~5 条属正常（按人去重 + CRM 后改数），只写进逐日表 footer 解释，**不修改明细**；超过 20 条才去查是不是又出现重挂 / 补录。
5. **异常识别** —— 盯零成交媒介、净负金额（退款冲减）、「有金额但成交人数 = 0」、最新日建档暴涨暴跌、公共账号（`网电公账 11013` / `三方公用 13125`）占比，以及积压补录污染单日口径的日子（这类日要单列剔除，不能当趋势拐点）。
6. **跨月常量体检** —— 报告里任何日期、人数、金额都要能在 `sanfang.json` 里找到出处，正文不许写常量；跨月后先 grep 上个月的月份串，防止「10-01~10-19 已并入 10-20」这类写死文案在新月份变错。
7. **报告视觉门禁** —— ECharts 横向条形图容器高度随条数动态给（否则类目标签被自动隐藏）、4 张表跨组同档联动高亮（同一行同一档恰好 2 格）、单日窗口无环比时显示「新周期首日 · 无可比日」而不是拿上月存档凑。
8. **月报重出** —— 上月报告可单独重出：导上月区间 → **备份当月四件套** → 写上月 window → 重跑 baseline / analyze → 独立文件名输出（不覆盖日报主文件）→ **恢复当月四件套并重跑复核 md5**。
9. **定时任务闭环** —— 每天 08:00 的「三方营销日报」只负责「加载本 Skill 并按 SOP 执行」，执行逻辑、汇报格式、口径全部收归本文件单一真源，不用回去堆长 prompt。
10. **留痕** —— 向自动化自己的 `memory.md` 追加一条高层摘要（窗口、合计、最新日环比、异常、校验结果、报告 md5 / 留档名），不把报告全文写进去。

## 四、数据口径铁律（违反必出错）

1. **统计区间 = 当月 1 号 ~ 前一天；合计一律取区间报表**，不叠加本地存档、不推算、不补录。
2. **逐日明细只列 CRM 实际持有 `>= queryable_start` 的天数**，更早的日期不画、不累加。
3. **差异只能解释、不能修补**：按人去重 + CRM 后改数造成的差额写进 footer 对账，超过 20 条才查重挂 / 补录。
4. **「录单」= 系统字段「建档量」**（用户确认），JSON 字段名仍是 `建档量`，只改显示文本。
5. **一律用 detail 明细行逐条加总，绝不用报表自带的「媒介类型汇总行」** —— 该行的 `成交_总人数` 有 bug（汇总写「新客 4 + 老客 2」，总人数却填 2）。金额 / 录单 / 来院三列两口径一致，仅成交人数受影响。
6. **成交人数只统计成交单**（退款不计人数）；成交金额是**净额**（退款冲减）→ 会出现「人数为正、金额为负」。恒等式：新客 = 新客首次 + 新客二次，总人数 = 新客 + 老客。
7. **公共账号单列**：`网电公账(11013)`、`三方公用(13125)` 不是真人咨询师，退款无归属归集于此，不要混进人均 / 排名。
8. **「有金额、成交人数 = 0」的明细行真实存在**（如某媒介数万元 0 人），不是 bug；这类金额要在结论里单列，不能拿去算人均。

验收标准（用户原话）：**「我只保证统计的数据和当天看到的数据是一样就行」** → ① 每日数字 ≡ 当天 CRM 看到的；② 区间合计要和 CRM 区间报表对得上。出数前先拿用户的报表当基准对一遍，别等他说「还是不对」。

## 五、每日 08:00 定时任务执行 SOP

| 步 | 动作 | 关键点 |
|---|---|---|
| ① | 前置连通性 | `Test-NetConnection` 测 TCP 80，`True` 才继续；`PingSucceeded=False` 不代表离线（防火墙拦 ICMP），只有 TCP 失败且 ARP Unreachable 才是真离线 |
| ② | 跑一键脚本 | 工作目录 `gd-crm-媒介日报\`，**不带参数**（= 昨天），后台运行并等结果 |
| ③ | 判成功 | 累计行必须出现 + 各步退出码为 0；缺累计行 = 假成功 → 判失败 |
| ④ | 取数汇报 | 数字一律从 `sanfang.json` 现算，禁止手写常量；转化率、客单价、异常清单都由此得出 |
| ⑤ | 交付校验 | `verify_days.py` 单日四项与区间逐项一致；`check_group_hl.py` 20/20 PASS；`check_charts.py` 类目标签全显；HTML 含最新日、**不含次日**、不含上月月份串 / 跨月写死文案 |
| ⑥ | 失败处理 | 内网不通 / 登录失败 / 接口报错 / 假成功 → 如实报失败原因与报错，不生成占位数字、不推算、不沿用旧报告 |
| ⑦ | 汇报模板 | 固定结构：报告路径 → 区间 → 合计 → 最新日 + 环比 → 异常 → 一句话结论；附口径差与校验结果 |
| ⑧ | 留痕 | 向自动化 `memory.md` 追加高层摘要，不写全文 |

## 六、交付门禁与校验脚本

| 脚本 / 检查 | 查什么 | 通过标准 |
|---|---|---|
| `verify_against_crm_export.py <CRM导出.xls>` | 拿用户亲手导出的报表逐媒介并排比 | 逐项对得上 |
| `verify_days.py <日期>` | 单日 xls 四项 vs 区间报表 | 逐项一致 |
| `check_group_hl.py` | 4 张表 × 5 档的跨组同档联动高亮 | **20/20 PASS**，每行恰好 2 格亮 |
| `check_charts.py` | ECharts 横向条形图类目标签是否全显 | 全显 |
| HTML 边界体检 | 含最新日、不含次日、不含上月写死文案 / 常量 | 无残留 |
| `analyze_sanfang.py` 累计行 | 分析步骤是否真跑完 | 必须打印，否则判假成功 |

另有一条易漏的 CSS 坑：全局 `th,td{white-space:nowrap}` 会把口径表里的长文案右侧硬裁，`.scope-tbl` 必须允许换行，媒介 / 逐日表保持 nowrap。

## 七、已知坑速查（节选，完整版见 `SKILL.md`）

| 坑 | 症状 / 解法 |
|---|---|
| 内网访问走系统代理 | urllib 必须 `ProxyHandler({})`，否则走本地代理失败 |
| 用 requests 登录 | 8080 报表服务不能带 80 端口 CRM 的 cookie，requests 不按端口隔离 → IIS 伪装 404；**必须用 Playwright 浏览器**并显式指定 chromium 路径 |
| 导出 Excel 只调一步 | `exportExcel('report1')` 只弹选项框，真正下载要调 `report1_saveAsExcel2(...)` 并用 `page.expect_download()` 接住 |
| 登录返回值判断 | 返回 `{"statusCode":"200"}` 是**字符串**，别用 `== 200` |
| CRM 停机后的空日 | 报表只有表头，`.get(f, 0.0)` 兜底，别回退成 `tot[f] += ...` |
| 残缺日数据残留 | 不要留在 `data\raw\daily\`，会永久残留；隔离到单独的 `_partial_*` 目录 |
| 「上月查不到」误判 | 月初只做按天归并（单日查仍空），但**整月区间数据保留可导出**；补上月要整段查一次导出，不要在当月窗口里二分 |
| 项目非 git 仓库 | 生成类脚本要自己留档（`history\`），主报告现已自动留档 |
| 改了还是不行 | 源目录 + `history\backup_*` 存在副本，**实际跑的是哪份要按文件名 / md5 判断**，不是「我改过了」 |

## 仓库结构

```text
gd-crm-sanfang-daily/                  ← 仓库根
├── README.md                          ← 你正在看的这份
├── .gitignore                         ← 排除凭据、数据、留档
└── gd-crm-sanfang-daily/              ← Skill 包（可整个拷进 skills 目录）
    ├── SKILL.md                       ← 执行逻辑唯一真源（口径 / SOP / 门禁 / 已知坑）
    ├── test-prompts.json              ← 13 条触发 / 边界测试用例
    ├── tools/sync_runtime.py          ← 源机器用：把生产脚本同步成可移植副本
    └── runtime/                       ← 可部署的运行时
        ├── DEPLOY.md                  ← 新电脑部署完整步骤
        ├── run_daily.py               ← 一键入口
        ├── ... 共 14 个 .py           ← 六步流水线 + 4 个校验 + 月报重出
        ├── assets/echarts.min.js      ← 图表库（随仓库分发，约 1 MB）
```

故意**没有**进仓库的：`config.local.json`（账号密码）、`data/`（原始 xls 与中间 json，含真实业绩）、`history/`（历史报告留档）、`*.html` / `*.xls`（生成物）、`probe*.py` 与备份副本（一次性调试脚本）。跑一次脚本，前面几类就会自动产生。

## 新电脑部署（clone 即用）

```bash
git clone https://github.com/Jerry-Tang95/gd-crm-sanfang-daily.git
cd gd-crm-sanfang-daily/gd-crm-sanfang-daily/runtime

python -m pip install -r requirements.txt
python -m playwright install chromium
copy config.example.json config.local.json   # Windows；填 username / password
python run_daily.py                          # 不带参数 = 昨天，约 1~8 分钟
```

产出同目录的 `三方营销媒介分析报告.html`。**先确认能连内网 `192.168.16.138:80`**，自检命令、跑完的 4 个校验脚本、判成功（防假成功）与定时任务重建说明全在 [`runtime/DEPLOY.md`](gd-crm-sanfang-daily/runtime/DEPLOY.md)。

脚本已做 4 类可移植改造：解释器用 `sys.executable`、浏览器默认用 Playwright 自带（可用 `CRM_CHROME` 指定）、内网地址可用 `CRM_BASE_URL` 覆盖、图表库改读 `runtime/assets/`。**源目录一个字没动**，本机每天 08:00 的定时任务不受影响。

只装 Skill、暂时不部署脚本时：

```bash
cp -r gd-crm-sanfang-daily ~/.workbuddy/skills/
```

Windows 下复制到 `%USERPROFILE%\.workbuddy\skills\`，目录名即 skill 名，别改。但这时 skill 只会告诉你「缺什么」，不会自己造数据 —— 要出数仍得部署 `runtime/`。

## 30 秒验证

问 **「跑一下今天的三方营销日报」** → 应加载本 skill，用托管 python 跑 `run_daily.py`（不带参数），并汇报实际统计区间、区间合计、最新一天四项核心数。

再问 **「用云客 CRM 拉一份团队周报」** → 应**不**触发本 skill（见下方边界）。

## 什么时候不该用

| 用户说 | 该走哪 |
|---|---|
| 云客 CRM / 团队周报 | `yunke-crm-periodic-report`（外部 SaaS，omni-cli 命令族，与本系统无关） |
| 网电咨询报表 / 现场月报 / 网络月报 | `wangdian-monthly-report`、`xianchang-monthly-report`、`network-report-build`（三套医疗 Excel 报表） |
| 填这周的周总结 | `weekly-report-fill`（消费本流程产出的 `sanfang.json`，共用取数层） |

不是「答不上来」，而是这些场景有更专业的入口。

## 测试用例（全部 13 条，来自 `test-prompts.json`）

`test-prompts.json` 未声明 `minimum_pass_rate`，建议按 **13/13 全通过**验收。

### 应触发（5）

| 提问原文 | 期望行为 |
|---|---|
| 定时任务触发：按 Skill 跑今天的三方营销日报 | 严格按 SOP ①~⑧ 跑完整闭环：先测 TCP 80 → 一键脚本 → 检查 analyze 累计行（缺则判假成功报失败）→ 从 `sanfang.json` 现算数字 → 逐项校验 → 固定模板汇报 → 追加自动化 memory 摘要；不带参数、不手工指定窗口 |

| 报告里的成交人数跟我在 CRM 看到的不一样，查一下 | 先拿用户的 CRM 导出跑 `verify_against_crm_export.py` 逐媒介比对，检查是否误用媒介类型汇总行、是否叠加存档 |

### 边界（5）

| 提问原文 | 期望行为 |
|---|---|
| 脚本报错了但 HTML 报告还在，能用吗 | 判为**假成功**：查 analyze 累计行与四步退出码；如实报失败，不沿用上一版报告 |

## 三条硬规矩

1. **合计一律取 CRM 区间报表**，不叠加本地存档、不推算、不补录；查不到的日期不纳入。
2. **不伪造任何数据**。内网不通 / 登录失败 / 接口报错就如实报失败，不生成占位数字、不沿用旧报告冒充新数据。
3. **没有 `analyze_sanfang.py` 的累计行 = 假成功**。此时 `gen_report` 可能拿旧 json 出一份「看起来成功」的 HTML，必须判失败。
